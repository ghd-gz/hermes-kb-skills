# 共同知识库架构规范

## 核心原则

**一份数据，两种观察方式。**

知识库是存放在服务器本地（或Git仓库）的一组 `.md` 文件。人类通过目录结构浏览，Agent 通过 frontmatter 元数据检索。同一份文件，两种使用方式。

## 目录结构（6层内容 + 2层管理）

```
知识库根目录/
├── 000-索引/                # 场景目录总览（给人看的知识地图）
├── 100-项目与专家/          # 场景定义（scope/边界/内容索引）+ 专家定义
├── 200-概念与方法/           # 概念（术语定义）+ 方法论（分析框架/流程）
├── 300-工具与SOP/           # 工具（脚本/配置/使用说明）+ SOP（可执行步骤）
├── 400-案例/                # 真实实战记录（背景→过程→结果→启发）
├── 500-事实/                # 不可变物理事实（数据/配置/时间线/路径）
├── 600-对话归档/            # 按专家名+日期的全量对话归档
└── 700-系统维护/            # 知识库自身的维护文件
```

**命名规则：**
- 目录和文件名用英文
- 一个概念一个文件，不写大篇综述
- 200-、300-、400- 下按场景/专家名分子目录

## YAML Frontmatter 协议

每个知识正文 `.md` 文件头部必须包含：

```yaml
---
type: concept | method | sop | case | tool | fact
discipline: philosophy | logic | physics | mathematics | systemics | aesthetics | psychology | business
status: seed | growing | stable | proven
tags:
  - 关键词1
  - 关键词2
---
```

### type — 6类知识分类

| type | 用途 | 出现位置 |
|------|------|---------|
| `concept` | 术语定义、核心概念 | 200-概念与方法/ |
| `method` | 分析框架、完整方法流程 | 200-概念与方法/ |
| `sop` | 可执行的步骤流程（一步步照着做） | 300-工具与SOP/ |
| `case` | 真实场景案例（结构化：背景→过程→结果→启发） | 400-案例/ |
| `tool` | 工具说明、配置、使用场景 | 300-工具与SOP/ |
| `fact` | 不可变事实基础（数据、配置、时间线） | 500-事实/ |

场景定义文件和管理目录用额外2类：`scene`（场景定义，在100-目录）、`index`（索引看板，在000-目录）。

### discipline — 8个元学科

| 学科 | 内核 | 典型对应 |
|------|------|---------|
| philosophy | 本体论、认识论、价值判断 | 矛盾论、伦理学、意义追问 |
| logic | 推理规则、结构化拆分 | 德尔菲法、正向/逆向推理 |
| physics | 客观因果、第一性原理 | 世界模型、物理边界 |
| mathematics | 形式系统、量化描述 | 映射关系、统计 |
| systemics | 反馈、涌现、层级、控制论 | 系统架构、闭环控制 |
| aesthetics | 感知判断、形式秩序 | 设计原则、排版配色 |
| psychology | 认知偏好、动机与归因 | 决策偏差、认知模型 |
| business | 市场、客户、竞争、财务 | 商业策略、投资分析 |

### status — Agent推理就绪信号

| 值 | 含义 | Agent 行为 |
|----|------|-----------|
| `seed` | 刚入库的原始笔记 | 只可复述，不可展开推理 |
| `growing` | 已基本结构化，但边界不完整 | 可回答问题，遇到边界说「还不够」 |
| `stable` | 内容完整，有定义/流程/案例/边界 | 可直接引用做独立推理 |
| `proven` | 经过至少一次实战验证 | 最优先引用（仅用户手动标注） |

## 场景驱动读取工作流

```
用户提问 → 场景识别（关键词匹配）
  │
  ├── 匹配成功 → 读场景定义（constraints/experts/assets）
  │              → 按资产路径加载KB文件
  │              → 注入约束 + 激活专家 → 综合推理
  │
  └── 未匹配 → 降级全文搜索 → 返回匹配结果
```

**工作原理：**
1. 场景索引是独立的JSON文件（存储在KB目录外部），内含每个场景的触发关键词、KB条目引用、约束、专家列表
2. **纯关键词匹配**，不做语义推理——用户主动提场景词才触发
3. 一个复杂问题可叠加多个场景视角（主导场景60%+权重）

## 交互式写入工作流

Agent在对话中自动判断内容价值，按三叉口路由写入：

```
知识类（concept/method/sop）→ 写.md到对应目录
文件类（case/tool/fact）    → 保存原始文件到对应目录
对话类                     → 精排版后保存到600-对话归档/
```

写入前经过三道质量门：≥3句实质性内容、去重检查、不确定先问用户。

写入优先级（P0-P5）：
- P0：用户说「记录一下」→ 无条件写入
- P1：可复用方法论/决策框架
- P2：新概念/定义
- P3：完整实战案例
- P4：新工具/配置（已验证）
- P5：重要事实（被纠正过的）

## 关键原则

1. **type=fact 仅限物理事实**。讨论产物（分析、推演、方案比较）都属于 case/method/concept
2. **status 不是完成度**，是 Agent 能不能用这个知识做推理的信号
3. **对话归档用原始 .md 文件**，不做 docx（容量限制会截断内容）
4. **归档顺序**：先原始资产（案例/工具/事实）→ 归纳概念方法 → 更新索引 → 对话归档（最后做最重的）

## 使用方式

加载本 skill 后告诉 Agent：「我们来建知识库」或「把我们讨论的内容归档」。

Agent 会自动：
1. 按场景识别用户当前在做什么
2. 从知识库加载相关的概念/方法/案例
3. 对话中产生的新知识按分类自动归档
4. 需要用户确认的内容先问再写
