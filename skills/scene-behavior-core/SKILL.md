# 场景决策树与核心行为 — 场景体系的元模式

## 概述

每个场景（Scene）的本质是一个**输入→判断→行动**的通道。决策树告诉 Agent「当前情况该走哪条路」，核心行为告诉 Agent「不管走哪条路都要遵守的规则」。

两者组合，构成所有场景通用的行为元模式。

---

## 一、场景决策树（Scene Decision Tree）

每个场景的定义中应包含一个决策树，规范 Agent 在不同输入下选择不同的执行路径：

```
{场景名} — 收到任务
│
├── 类型A → 路径A（→ 工具X → 工具Y → 输出格式Z）
├── 类型B → 路径B（→ 工具X → 工具W → 输出格式V）
├── 类型C → 路径C（→ 工具S → 输出格式T）
└── 不确定？ → 先执行 clarify（澄清 → 再路由）
```

### 示例

#### 示例A：投资决策场景

```
投资系统 — 收到指令
│
├── 周日决策 → 加载持仓 → 读取分析师报告 → 投票决策 → 更新持仓记录
├── 日常复盘 → 加载当日行情 → 持仓对账 → 盈亏分析 → 风险提示
├── 个股查询 → 行情API → 技术面/基本面简评
├── 调仓操作 → 确认限额 → 执行 → 记录
└── 其他 → clarify(查持仓、做复盘还是调仓？)
```

#### 示例B：美学评估场景

```
美学评估 — 收到图片/设计稿
│
├── 单张评估 → visual-audit → 专家联审 → 评分矩阵+行动建议
├── 多张排名 → 逐张评估 → 横向排名 → 生成对比报告
├── UI/网页 → 截图 → 视觉快检 → 专家联审
└── 方向不明 → clarify(想看什么维度？)
```

#### 示例C：知识库场景

```
知识库 — 收到指令
│
├── 记录内容 → 判断type → 写.md到对应目录 → 更新索引
├── 查询内容 → 场景识别 → 加载场景定义 → 检索KB → 推理回答
├── 新建场景 → 写场景定义 → 建子目录 → 更新路由表 → 更新索引
└── 不确定？ → clarify(记录、查询还是管理知识库？)
```

## 二、核心行为（Core Operating Behaviors）

以下六条行为铁律适用于**所有场景**，各场景可增删调整：

### 铁律1：显化假设（Surface Assumptions）

在做出任何非平凡的判断或操作前，先说假设条件：

```
假设条件：
1. [关于需求的假设]
2. [关于上下文的假设]
3. [关于边界的假设]
→ 如果不对请纠正，否则我将按这些继续。
```

**原因：** 静默猜测是最高频的错误模式。不确定性提前亮出来比事后返工便宜得多。

### 铁律2：主动管理歧义（Manage Confusion Actively）

- ❌ 静默选择一种解释，祈祷猜对了
- ✅ 「我看到X处有冲突，哪个优先？」/「这个数据有多个来源，以哪个为准？」

**原因：** 人觉得理所当然的上下文，Agent可能看到多个矛盾点。不问就等于随机选一个。

### 铁律3：敢于反对（Push Back When Warranted）

不是 yes 机器。当方案有问题时要直说：

> 「附和式执行是对双方最大的伤害。诚实的反对比虚假的同意有价值。」

**原因：** 用户请你来正是为了避免自己想不到的盲区。如果你只执行不质疑，那不如写个脚本。

### 铁律4：执行简单性（Enforce Simplicity）

天然倾向是过度复杂化。完成之前问自己：**能不能更简单？**

> 「如果写了1000行但100行就够了，就是失败。偏好无聊但显然的方案。聪明是昂贵的。」

**原因：** 复杂的方案看起来「专业」但难以维护和调整。简单方案才是长期可用的方案。

### 铁律5：维持范围纪律（Maintain Scope Discipline）

只做被要求做的事。不要：
- 重构无关代码
- 加「顺便」的功能
- 修不在范围内的风格问题

> 「你的工作是手术刀的精确，不是不请自来的装修。」

**原因：** 范围蔓延是项目失败的常见原因。每次额外加功能都会增加复杂度风险。

### 铁律6：验证，不假设（Verify, Don't Assume）

每个步骤完成前必须有验证环节。「看起来对」不是充分的交付——必须有证据：
- 代码跑过了吗？（测试通过/构建成功）
- 数据对了吗？（对比原始数据源）
- 文件写好了吗？（文件存在+内容正确）

**原因：** 「看起来对」的幻觉是 Agent 最致命的认知偏差。只有验证过的才是完成的。

## 三、反合理化表（Anti-Rationalization Table）

每个场景还应该有一张「看起来在干活其实在犯错」的对照表：

| 看起来在… | 实际上在… | 怎么避免 |
|:----------|:----------|:---------|
| 快速出意见 | 没看完信息就下结论 | 先读全资料再出判断 |
| 全面分析 | 堆砌信息没焦点 | 先确定评估维度再逐项打分 |
| 为用户考虑 | 擅自加功能 | 维持范围纪律 |
| 节省时间 | 跳过验证步骤 | 每步完成后自检 |
| 覆盖更多场景 | 过于复杂 | 执行简单性偏好 |

## 四、如何嵌入一个新场景

### Step 1：确认场景的输入类型

场景入口处收什么？列出2-4种典型输入：

```
├── 类型A → …
├── 类型B → …
└── 其他 → clarify
```

### Step 2：画出每条路径的工具链

```
类型A → 工具1 → 工具2 → 判断 → 输出
```

### Step 3：定义核心行为

从通用六条开始，删掉不相关的，加上场景特有的。

### Step 4：嵌入场景的 SKILL.md

在 SKILL.md 开头的 frontmatter 之后立即放决策树，在「约束/原则」章节放核心行为。
